1. Executive Summary

FUXA is an open-source, full-stack SCADA/HMI platform. A Node.js/Express server acquires live process data from industrial devices (Modbus, OPC UA, S7, BACnet, MQTT and 13 more), historizes tag values into SQLite/InfluxDB/ QuestDB/TDengine, exposes a secured REST API over HTTP, and pushes live values to a rich Angular 18 single-page client over Socket.IO/WebSocket. The client provides a drawing-style Editor in which operators compose SVG views, bind device tags to graphic elements and widgets, and configure alarms, notifications, schedulers, reports and recipes. The finished project is served to plant operators as a fullscreen HMI (Home), a simulation Lab, a kiosk mode, an Electron desktop app, and — in this fork — a browser-based AR mode and a custom iPTran leak-detection schematic widget.

3. Server (server/)

3.1 Boot sequence — main.js (683 lines)

  1. Parse CLI args (nopt): --port, --userDir, --env; env userDir, BASE_PATH.
  2. Resolve workDir (<userDir>/_appdata), copy settings.default.js → _appdata/settings.js on first run, merge missing fields when the version differs (deepMerge).
  3. Read user overrides _appdata/mysettings.json (language, uiPort, secure settings, smtp, daqstore, alarms, logs, nodeRed, swagger…).
  4. Generate a random JWT secret if secureEnabled without secretCode (fail-safe).
  5. Create runtime directories: _appdata, _db, _reports, _upload_files, _images, _widgets, _webcam_snapshots, _logs.
  6. Create the HTTP(S) server with Express + Socket.IO (path = BASE_PATH + /socket.io, EIO3 compat).
  7. Optional BASE_PATH reverse-proxy support: rewrites <base href> and asset URLs in memory.
  8. Static routes: Angular shell routes (/, /home, /editor, /lab, /device, /view, /ar, …), /resources, /_images, /_widgets, webcam snapshots (token-protected).
  9. Morgan request logging to _logs/api.log (level from settings), optional Swagger UI at /api-docs.
  10. Call FUXA.init() (fuxa.js) which initializes the runtime (§3.2) and mounts the API; on init-runtime-ok (or a 60 s timeout) start listening on uiPort (default 1881).
  11. Webcam snapshot cleanup scheduled daily at 01:00 (node-schedule) when enabled.
  12. SIGINT handler stops the runtime cleanly; uncaughtException logger keeps the process alive.

3.5 Plugin system — server/runtime/plugins/

FUXA ships drivers as npm packages that are installed at runtime into an isolated package directory (_pkg): npm-runtime-service.js implements install/uninstall/list of npm packages outside the main node_modules; index.js keeps a registry (Plugin records: name/module/type/version/group) with groups connection-device, connection-database, chart-report, service (node-red). device.loadPlugin(type, module) hot-swaps the driver module for a device type. The editor Plugins page drives this via /api/plugins.

4.4 Widget pipeline (client side)

Placement: Lib Widgets panel → LibWidgetsService.widgetSelected(path) → editor fetches the SVG, stores the content in localStorage keyed by the widget path, and switches to own_ctrl-image placement mode. Rendering (html-image component): the stored/saved svgContent is parsed, scripts are extracted and processed (SvgUtils.processWidget rewrites exported variable hooks and renames element IDs with a GUID to avoid DOM collisions), the sanitized SVG is injected, and the script is executed with a generated module. The 15 exported variables land in property.varsToBind where each row binds to device/tag via flex-widget-property. Tag updates arrive through Socket.IO and are pushed into the widget via putValue(id, value); widget interactions call postValue(id, value) back to FUXA. Placed widgets freeze their content at placement time — new file revisions require re-placement or a new view (version-per-view convention).

6. Widget System and the iPTran Schematic

6.1 FUXA dynamic SVG widget standard (docs/HowTo-Widgets.md)

  • Pure SVG + embedded <script>; bindable globals declared between //!export-start///!export-end, named by type prefix: _ps_ string, _pn_ number, _pb_ boolean, _pc_ color.
  • Inbound updates via putValue(id, value); outbound commands via postValue(id, value).
  • Widgets using timers must self-destruct when removed (MutationObserver/element check).
  • Editor lists widgets from subfolders of _widgets only (GET /api/resources/widgets, admin-gated in secure mode).

8. Security Model

  • Optional secureEnabled: JWT access tokens (jsonwebtoken) with configurable expiry, optional HttpOnly refresh-cookie flow, bcrypt password hashes, role groups (admin/operators/guests) checked per API route and for the widget/image galleries.
  • Rate limiting: generous API window (1000 req/5 min) and tighter auth window (100/5 min) via express-rate-limit.
  • CORS allowlist (settings.allowedOrigins, wildcard patterns supported); BASE_PATH reverse-proxy support.
  • Settings disclosure guard: daqstore URLs/credentials stripped from API responses (api/index.js).
  • Snapshot route protected by token when security is on; webcam snapshots cleanup by retention.

9. Known Limits and Architectural Roadmap

Findings from the codebase review (full design in the repository notes):

  1. DAQ write path — single INSERT per tag per poll with drop-on-overload; plan: in-process bounded batching queue (daq-queue.js) + transactional SQLite writes (WAL, prepared statements), preserving source timestamps (device-utils sets tag.timestamp already).
  2. Edge-to-cloud store-and-forward — no offline buffer today; plan: SQLite spool (WAL ring buffer) + forwarder with exponential backoff, or a Fluent Bit tail adapter over JSON-lines outbox.
  3. Plugin architecture — drivers are npm-runtime packages but the registry and device-type dispatch are hardcoded (device.js if/else, DaqStoreTypeEnum); plan: IProtocolPlugin/IDBPlugin interfaces + external plugins directory (fuxa.plugin.json manifests) so protocol/DB drivers drop in without core edits.
